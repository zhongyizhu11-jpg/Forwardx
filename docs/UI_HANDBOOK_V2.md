# ForwardX UI Handbook V2

> Professional Network Control Plane —— 精密、克制、实时、可靠、有空间层级。

这份文档是 ForwardX 界面的唯一判据。写组件之前先读它；和现有代码冲突时以它为准。

V1（`UI_HANDBOOK_CN.md`）仍然有效的部分是排版原则和无障碍要求；尺寸、颜色、
圆角、间距这四项全部由 V2 取代。

---

## 零、为什么要有 V2

V1 解决的是「好不好看」。它做到了一部分，但没解决真正的问题：

**ForwardX 已经不是一个后台管理面板了。** 它管的是节点、路径、流量和交付，
是一套网络控制台。而界面语言还停在「标题 + 卡片 + 表单」——
每个页面都是容器套容器，每个概念都是一个圆角矩形，所有信息一样重。

V2 要换的是这件事：

```
用户真正操作的对象：  节点 Node → 路径 Path → 流量 Flow → 客户端 Delivery
界面也应该围绕这四个概念，而不是围绕「页面 → 卡片 → 表单」。
```

一句话概括整套语言：

> **节点是点，链路是线，转发是流，状态是信号，数据是反馈。**

## 一、表面层级：不是所有信息都需要一个圆角矩形

V1 最普遍的结构是：

```
页面 → Card → Card → Card → Button
```

全部都是容器。结果是每一层都在画框，而框本身不携带任何信息。

V2 规定四层，**只有 L1 是一块面**：

| 层 | 是什么 | 怎么画 |
|---|---|---|
| **L0** 页面背景 | 整页的底 | 浅灰 `--fx-l0-page`，**不放内容**，只负责托住白卡 |
| **L1** Surface | 真正需要成为一个模块的区域 | **纯白 + 16px 圆角 + 不描边** |
| **L2** Content Group | Surface 内部的分组 | 间距和 Divider 优先；确实要再分一格时用 `--fx-l2-group`（= 页面底那个灰） |
| **L3** Interactive Element | 按钮、输入框、Segment、Chip、Switch | 白底，10px 圆角；放在白卡里才描边 |

**分层靠的是「灰底托白卡」这一次底色差，不是靠边框。**

这条要展开说，因为它被推翻过一次，代价不小。

上一版每层都有自己的一点灰（页面 #f4f4f6、分组 #f7f7f9、输入框填充 #f1f1f4）。
单看每块都「只是浅了一点点」，合起来一屏就有四种灰，而它们谁也没在表达信息。
更隐蔽的是那些灰全都**偏蓝**（#55555f 的蓝比红多 10），一屏冷调的灰读起来就是
「发闷」。

所以先做了一轮「全局去灰」：四层全刷白，界限交给 1px 边框。结果是另一个毛病 ——
**没有底色差之后，边框得独自扛起全部的「这是一块区域」，一屏几十条 1px 灰线，
看着像线框图，不像成品。**

两轮之间真正的区别不是灰多灰少，是**灰在什么位置**：

- **灰当面**（卡片自己是浅灰、输入框填充是浅灰）→ 发闷。这个不要。
- **灰当底**（页面是浅灰、卡片是纯白）→ 白卡浮起来。质感就来自这里。

所以现在只留一次底色差，而且方向固定：**底灰、面白**。
L0 与 L1 的对比只有 1.13:1 —— 它不需要看得清，只需要让白块有个边界感；
真正的信息层级仍然由字号、字重和间距承担。

既然有了底色差，**卡片就不再描边**：底色差和边框说的是同一句话「这是一块独立
区域」，说两遍读起来就是重。iOS 的分组卡片从来不描边，就是这个道理。
边框只留给**放在白卡里面**的东西（输入框、Chip、Divider）—— 那里没有底色差
可用，线是唯一的办法。

中性色一律 **R=G=B**（这条没变，偏蓝的灰是上一轮的真正病根）。
悬停/按下用 `--fx-hover`，它是**瞬时**反馈，不是静态的面。

### 除了这一次底色差，谁来成形

- **选中态**：整块反白（黑底白字）。分段控件的选中项就是这么画的 ——
  比「灰底 + 白滑块 + 投影」更明确，一屏扫过去黑的那块就是「你在这里」。
- **静态标记**（TCP / 计数徽标）：描边成形，底色留白。
- **输入框**：在白卡里是白底 + 描边；直接坐在灰页面上时（移动端的筛选条、搜索框）
  反过来 —— 白底、不描边，跟卡片同一套逻辑。
- **进度轨道**：用线色 `--fx-stroke-weak`，一条 1px 的轨道本来就更像线。

对照一下主机卡。V1：

```
┌─────────────────────────┐
│ ┌─────────────────────┐ │   ← L1 里又套了三个 L1
│ │ 主机信息             │ │
│ └─────────────────────┘ │
│ ┌─────────────────────┐ │
│ │ CPU RAM Disk         │ │
│ └─────────────────────┘ │
│ ┌─────────────────────┐ │
│ │ Traffic             │ │
│ └─────────────────────┘ │
└─────────────────────────┘
```

V2：

```
┌─────────────────────────┐
│ ● DW TW        v2.2.196 │
│   Taiwan · 78.105...    │
│                         │
│ CPU   ━━ 2%             │   ← L2，靠间距分组
│ RAM   ━━━━━ 25%         │
│ DISK  ━━━━ 17%          │
│ ─────────────────────── │   ← L2 之间用 Divider
│ ↓ 40.4 KB/s  ↑ 2 KB/s  │
│ ↓ 6.09 GB    ↑ 2.21 GB │
│                         │
│ Running 12d 5h      ··· │
└─────────────────────────┘
```

同样的信息，少了三个框 —— 现在连最外面那一个框也没有了，剩下的是一块白。

## 二、ForwardX 的核心视觉组件：Path

**这是整个 V2 最重要的一件事。**

凡是表达网络关系的地方，都用同一套 `NetworkNode` / `NetworkEdge` / `NetworkPath`
（`client/src/components/network/NetworkPath.tsx`），不再各写各的。

为什么：面板里「入口 → 出口」这件事，隧道页、规则页、转发链、转发组、链路诊断、
创建向导预览，一共有六处在画，六处画法都不一样 —— 有的两行带标题竖排，有的一行
加箭头，有的干脆写「入口主机：xxx / 出口主机：yyy」。同一个概念在一个产品里有
六种长相，用户每换一页要重新认一次。

而且「入口主机：」这种写法本身就是在**用文字解释空间关系**。空间关系应该由空间
表达：左边那个点就是入口，右边那个点就是出口，中间那条线就是它们的关系。

### 三种形态

竖排（三个及以上节点，或需要写清每一段）：

```
● Po0
  Guangdong
     │
     │  ForwardX
     │  8 ms
     ↓
● Jinx
  Hong Kong
```

横排（两个节点，横向空间够）：

```
● Po0 ─────────────── ● Jinx
  广东      8ms         香港
       ForwardX V1
```

分支（主备、多出口）：

```
● Po0
  │
  ├──── ● Relay HK-01
  │         │
  │         └──── ● Jinx
  │
  └ · · · ● Relay HK-02
            Backup
```

### 状态怎么画

判定统一由 `shared/networkHealth.ts` 给出，面板、服务端摘要、Telegram 推送共用
同一份词汇表：

| 状态 | 颜色 | 线型 | 含义 |
|---|---|---|---|
| `healthy` | 绿 | 实线 | 在跑，探测通过 |
| `degraded` | 琥珀 | 实线 | 在跑，但指标越界 |
| `down` | 红 | 虚线 | 该跑没跑，或探测失败 |
| `standby` | 灰 | 虚线 | 按设计就没在跑：备线、手动停用 |
| `switching` | 路径青 | 脉冲 | 正在切换（唯一的瞬时态） |
| `unknown` | 灰 | 虚线 | **没有结论** |

**`unknown` 单列一档是这套词汇表最重要的约定。**

「没上报过」不等于「正常」。把没有结论的东西显示成绿色，等于让一台已经失联的
机器看起来健康 —— 这是监控类产品最不该犯的错。所以任何判定函数拿不到数据时
一律回 `unknown`，绝不回 `healthy`；`rollUpNetworkHealth([])` 同理回 `unknown`
而不是 `healthy`，零个成员不代表一切正常，代表什么都不知道。

有了这套规则，**以后做主备线路、负载均衡、多出口都不用重新设计 UI**：一条待命的
备线就是「灰点 + 虚线」，切换的瞬间就是「脉冲」，规则已经在这里了。

## 三、字号：严格六档

数据型产品里数字本身就是视觉元素。刻度按「这个数字有多重要」分，不按「这行字
有多长」分。

| 令牌 | 桌面 | 移动 | 用在哪 |
|---|---|---|---|
| `--fx-size-display` | 32 / 36 | 28 / 32 | 首屏最大的数（总流量、在线数） |
| `--fx-size-metric` | 24 / 28 | 22 / 26 | 区块级的数（CPU、延迟） |
| `--fx-size-section` | 20 / 28 | 17 / 24 | 区块标题 |
| `--fx-size-primary` | 17 / 24 | 16 / 22 | 主要内容：名字、地址 |
| `--fx-size-secondary` | 15 / 22 | 14 / 20 | 次要内容：归属、说明 |
| `--fx-size-meta` | 13 / 18 | 12 / 16 | 标签、单位、时间戳 |

Tailwind 里写 `text-display` / `text-metric` / `text-section` /
`text-primary-type` / `text-secondary-type` / `text-meta`，行高跟着走，不用另写。

（后缀 `-type` 是为了避开 Tailwind 已有的 `text-primary` 前景色工具类。）

### 数字的写法

不要：

```
总延迟 8ms
```

要：

```
延迟
8 ms      ← 8 走 metric 档，ms 走 meta 档
```

一眼看到的应该是 `8`，不是「延迟」两个字。

### 等宽字体

IP、端口、版本号、流量走 `--fx-font-mono`。等宽不只是好看 —— 数字对齐之后一列值
扫下去能直接比大小。这也是基础设施类产品的气质来源。

### 移动端不是等比缩小

桌面是 **Control Plane**：一屏同时看列表、详情、拓扑。
移动是 **Operations**：看状态 → 看异常 → 开关 → 诊断。

所以移动端压的是间距和大标题，正文那几档基本不动 —— 把正文压小只会让人凑近看。

> **iOS 硬约束**：输入框 `font-size` 必须 ≥ 16px，否则 Safari 聚焦时会把整页放大。
> 这一条压过任何密度需求。

## 四、间距：4px 栅格

只允许这九个值：

```
4  8  12  16  20  24  32  40  48
```

| 场景 | 值 | 令牌 |
|---|---|---|
| 页面左右 | 16（移动 12） | `--fx-gutter` |
| 卡片内边距 | 16（移动 12） | `--fx-card-padding` |
| 卡片与卡片 | 12（移动 8） | `--fx-card-gap` |
| 区块与区块 | 32（移动 20） | `--fx-section-gap` |

不同页面各自决定间距是 V1 最大的不一致来源。

> **Tailwind v4 的坑**：`space-y-*` 编译成 `> :not(:last-child) { margin-block-end }`，
> 不是 v3 的 `> * + * { margin-top }`。两者命中不同的边，**会相加而不是相替**。
> 同时用等于间距翻倍 —— 这个 bug 在 V1 里藏了很久（设定 6px，实测 16px）。

## 五、圆角：分级，不是一个值

所有东西都圆会失去层级；所有东西都是**同一个**圆角同样会。半径必须跟着尺寸走。

| 令牌 | 值 | Tailwind | 用在哪 |
|---|---|---|---|
| `--fx-radius-control` | 10px | `rounded-md` | 按钮、输入框、Chip、Segment |
| `--fx-radius-card` | 12px | `rounded-lg` | 列表卡、小面板 |
| `--fx-radius-surface` | 16px | `rounded-xl` | 主 Surface、大容器 |
| `--fx-radius-modal` | 20px | 显式写令牌 | 对话框、Bottom Sheet |
| `--fx-radius-pill` | 999px | `rounded-full` | 徽标、状态胶囊 |

不要出现 `rounded-[13px]`、`rounded-[7px]` 这种当场拍的值。

## 六、高度：四级，靠它建立空间关系

**高级感不靠 shadow。** 普通卡片就是平的。

| 令牌 | Tailwind | 用在哪 |
|---|---|---|
| `--fx-elevation-flat` | — | 普通卡片：只有边框 |
| `--fx-elevation-card` | `shadow-card` | 需要一点点浮起的卡片 |
| `--fx-elevation-popover` | `shadow-popover` | 下拉、气泡、菜单 |
| `--fx-elevation-modal` | `shadow-modal` | 对话框、Bottom Sheet |

用户看到投影就知道「这是盖在上面的」，不用解释。

## 七、颜色：必须有语义

只有这几个。**一个颜色如果回答不了「它在说什么」，就不该出现在界面上。**

| 语义 | 令牌 | Tailwind | 说什么 |
|---|---|---|---|
| 中性 | `--fx-text` / `-secondary` / `-muted` | `text-foreground` 等 | 内容本身 |
| 健康 | `--fx-healthy` | `text-healthy` `bg-healthy-soft` | 在线、正常、成功 |
| 警告 | `--fx-warn` | `text-warn` `bg-warn-soft` | 降级、切换中、即将到期 |
| 故障 | `--fx-down` | `text-down` `bg-down-soft` | 离线、错误、破坏性操作 |
| 待命 | `--fx-standby` | `text-standby` | 备线、停用、未上报 |
| 路径 | `--fx-path` | `text-path` `border-path` | 网络关系、选中、流动的数据 |
| 交付 | `--fx-delivery` | `text-delivery` | **只给**订阅 / 客户交付 |

不写 `emerald-500`、`amber-400` 这类调色板颜色。类名里出现 `healthy` 才是在说事，
出现 `green-500` 只是在说好看。

**ForwardX 的品牌识别来自路径青（网络关系），不是到处刷一层品牌色。**

## 八、操作：一级最多两个

V1 的卡片底部一排图标：波形、诊断、刷新、编辑、垃圾桶、三点 —— 用户需要记忆
每个图标是什么意思。

V2 规定：

```
卡片一级操作最多 2 个，其余全部收进 ···
```

```
                              诊断    ···
```

`···` 里的顺序固定：

```
编辑
复制
禁用
────────
删除        ← 永远最后，永远红色
```

删除和其它操作之间必须有分隔线。破坏性操作是唯一需要在点之前就被看见的信息，
所以它保留红色 —— 那不是装饰。

## 九、创建流程：渐进式披露，不要超长表单

不要一次摊开二十个字段。分步，每步只问一件事：

```
Step 1  选择转发方式    端口转发 / 隧道转发 / 转发链 / 转发组
Step 2  选择路径        列出可用链路，带延迟
Step 3  目标            地址 / 端口 / 协议
Step 4  Review          把即将创建的东西画成 PathPreview，再确认
```

最后一步不是直接「创建」，而是先给出预览：

```
新转发
42.194.198.67:22222
        ↓
       Po0
        ↓
   ForwardX
        ↓
      Jinx
        ↓
217.116.172.44:22222
TCP + UDP
──────────────
取消              创建转发
```

这一步的价值是安全感：用户在点下去之前，看到的是他将要得到的东西本身，
而不是一份他填过的表单。

## 十、信息架构

```
ForwardX
│
├── 总览      System Health · Traffic · Attention
├── 主机      Nodes · Groups · Services · Tokens
├── 链路      Tunnel · Direct · Chain · Group · Route Policy
├── 转发      Rules · Groups · Traffic
├── 订阅      Nodes · Subscriptions · Delivery
└── 设置
```

对应的心智模型：

> 我有哪些机器 → 它们怎么连接 → 流量怎么走 → 怎么交付给客户端

### 总览要回答的不是「我有什么」

V1 首页告诉用户**我有什么**（一堆数字卡片）。V2 首页要告诉用户
**我现在需要处理什么**：

```
需要关注                           1
● 55
  主机离线
  最后在线 5天17小时前             >
△ HK-TW
  延迟 82ms · 较平均值 +41%        >
```

没有问题时，「需要关注」**整块不出现** —— 顶上那一行已经写了「✓ 运行正常」，
再来一块「一切正常」是同一句话说两遍。（这一节最初画的是一块写着「一切正常」的
区域，落地时改掉了。）

筛选依据是 `describeNetworkHealth(...).needsAttention` —— 注意 `unknown` 也算
需要关注，它是一个待查的问题，不是一切正常。落地后的几条约定：

- 顶上的数和列表出自同一次调用（`dashboard.health`），逐类对应：列表里有几处红的，
  顶上就写几处异常。
- 顶上按「最该先看到哪个」退档：有异常说「N 处异常」；没有异常但有降级说「N 处
  降级」—— 不能在列表里挂着琥珀色的同时写「运行正常」。
- 「还没接入」的主机（unknown）进列表但不计入异常：一步没做完，不是出了事。
- 按设计停着的不算异常：转发组的模板规则看子规则；主人被计费暂停的规则在管理员
  那边不算，在租户自己那边合成一行「转发已暂停」。
- 同一档状态里按「从根上往下」排：主机 → 隧道 → 转发组 → 转发。

### 列表和详情各管各的

列表负责**看状态**，详情负责**看数据**。不要让列表承担详情页的职责 ——
一台服务器占接近一屏，在 50 台的场景下效率会非常低。

主机页给两种视图：手机默认 Compact，点击展开 Detail。

## 十一、组件清单

新页面从这里挑，不要自己造：

```
AppShell · PageHeader · SectionHeader · Surface
Metric · MetricGroup · ResourceMeter · Sparkline
StatusDot · HealthBadge
NetworkNode · NetworkEdge · NetworkPath · PathPreview      ← 三个核心
HostCard · LinkCard · ForwardCard · SubscriptionCard
TrafficMetric · LatencyMetric
SegmentControl · SearchField · FilterBar · ActionMenu
BottomSheet · Dialog · Drawer
EmptyState · LoadingState · ErrorState · OfflineState
```

已落地：`StatusDot`、`HealthBadge`、`NetworkNode`、`NetworkEdge`、`NetworkPath`、
`PathPreview`；iOS 那一套 `GroupedList`（`ListSection` / `ListRow`）、导航栏、
标签栏；首页的 `AttentionSection` / `TrafficSurface` / `AccountSection`
（`client/src/features/dashboard/`）；主备策略的 `RoutePolicyPanel` /
`RoutePolicySheet` / `FailoverPolicyFields` / `PolicyBlocks`（`client/src/features/rules/`，
判断在 `shared/routePolicy.ts`），转发组的 `GroupFailoverPolicyFields`
（`client/src/features/links/`，同一份模型、同一块面板）；页头的 `SummaryStrip`、
手机上的流水行 `LedgerRow`、卡片底部的 `CardActions`（`EntityActions` 两个带字 + ···）、
设置页的 `SettingList` / `SettingRow`。其余按 Phase 推进。

**设置行**（`SettingRow`）：名字 + 说明在左，控件在右，行间一根细线（和分组列表同一条
`.fx-list-row`），不画框。控件是**一个**开关或复选框时 `asLabel`，整行都能点；这一项
自己的参数（阈值、天数）作为 children 跟在同一格里、在 label 外面。二选一、三选一用分段
控件，下面只摆选中那一种的字段 —— 不要把几种都画成并排的大卡片再标「当前使用」。

**卡片里的数**：一两个值写成设置行的行尾（「已开启 5 / 6」）；几个数并排才用摘要条。
不要一个数一个小框。

**宽屏两栏看容器，不看窗口。** 设置页宽屏是左边分区、右边内容；右栏里的分栏一律按
右栏自己的宽度切（`@container` + `@[42rem]:` / `@[58rem]:`），不写 `lg:` / `xl:` ——
侧栏收起、展开时同一个窗口宽度下右栏能差出 200px。

**条件行**（Policy 的画法）：一层一行，从上往下就是优先级。此刻起作用的那一行左边
一根 3px 的 `--fx-path` 竖条、字重加粗、右侧一个 `EntityTag tone="path"` 写「此刻」；
「本该轮到它、被上面那层压着」的那一行不高亮，但用 `--fx-warn-text` 写一句被谁压着；
其余的照常画。**不整行染色** —— 白块里再染一块面，就是又多了一层。

**规矩写在后半句的说明要能折行。** `ListRow` 的说明只给一行、放不下就截成「…」：
「在用的成员不健康满 60 秒就换下一个健康的；Agent 已判定失败的不等」在手机上被截掉的
恰好是规矩那半句。这种整句话用策略面板里 `SentenceRow` 那种写法（标题一行、说明照常折行）。

## 十二、写 CSS 的两条硬规矩

这一轮踩过的坑，写下来免得再踩：

**一、密度差异改令牌的值，不写覆盖选择器。**

V1 的移动端密度是 370 行覆盖规则，同一个选择器写两遍互相盖的事故出了六次
（写了不生效，回头才发现被后面同名的那条盖掉）。令牌只有一处定义，这类事故
从结构上不会发生。

**二、改完必须量，不能只看代码。**

Tailwind 工具类是 `(0,1,0)`；一条 `[data-slot="x"]` 也是 `(0,1,0)`，同特指度时
**后写的赢**。写了一条规则不代表它生效。改完在真实视口下用 `getComputedStyle`
读一遍，看截图只能判断好不好看，不能判断值对不对。

（同理：自己写的测量脚本也要验。V1 有一次量出来 39px 的「间距」是跨嵌套容器算的，
害我以为改动没生效，实际一直是对的。）

## 十三、重构顺序

不要一次性「把 UI 美化一下」，那样最后一定变成局部修补。

| Phase | 内容 | 状态 |
|---|---|---|
| 1 | Foundations：令牌、字体、间距、圆角、颜色、表面、状态体系 | ✅ |
| 2 | Visual Language：Node / Path / Edge / Flow / Health | ✅ |
| 3 | 核心三页：总览 → 主机 → 链路 | ✅ |
| 4 | 操作系统：Drawer、Bottom Sheet、ActionMenu、创建流程、诊断流程 | 部分：Sheet / 操作表 / 创建流程；诊断流程未动 |
| 5 | 转发系统：规则、链、组，以及 Route Policy 抽象 | ✅ |
| 6 | Subscription + Settings 迁移 | ✅ 设置页宽屏两栏 + 设置行；商店、套餐、个人资料、订阅 |
| 7 | Polish：Skeleton / Loading / Empty / Error / 转场 / 深色 / 响应式 | |

按 PR 拆的推进表（和这张表是同一件事的另一种切法）在
`FORWARDX_PRODUCT_UI_CN.md` 第八节。

最后再做一次全站视觉审计。

**最重要的一点：不要以「每个页面怎样变漂亮」为设计单位。**
先把 ForwardX 定义成 `Node → Path → Flow → Delivery`，然后让用户在整个系统里
始终看到同一种语言。
